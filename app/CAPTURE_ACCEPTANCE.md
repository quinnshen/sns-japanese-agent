# 分批录音：第一阶段验收

第一阶段完成「浏览器持续采集 → 分批上传本机 → 确认保存 → 完整性检查 → 本地回放」。
本阶段不接入 Google 转写和 GPT 翻译解析，也不需要配置这两项服务的凭据。
服务器默认处于采集模式；旧的整段转写入口需要显式设置 `ENABLE_LEGACY_PIPELINE=1`。
本次验收保持该开关关闭，不调用旧入口。

接口与记录格式见 [CAPTURE_PROTOCOL.md](CAPTURE_PROTOCOL.md)。

## 准备

1. 按应用说明安装本机后端依赖，运行 `app/backend/server.py`，并加载当前扩展。
2. 选择一个有声音、可正常播放的 YouTube 视频。保留当前正常播放限制：1 倍速，录制中不拖动进度、不换视频；缓冲超过允许范围时中断此次采集。
3. 点击 S，填写素材起点和终点。上传间隔在「调试信息」中，默认 **5 秒**，可在 **1–30 秒**范围内调整。
4. 点击「生成学习内容」后，扩展连接音频、跳到所选起点、启动录音并播放。上传间隔只是触发批次的目标值，浏览器实际发出批次的时刻可能不同，最后一个批次也可能更短。

视频总时长可以超过选取范围；当前限制按选取范围计算，最多 30 分钟。
第一阶段先验收 1–2 分钟和 5–10 分钟，不把 30 分钟以上压力测试作为这一阶段的完成条件。

### 开始按钮不可用或播放器持续转圈

- 点击「生成学习内容」后，面板会显示连接本机、准备音频和读取视频信息的进度。
- 视频信息尚未加载时最多等待 8 秒；音频准备和首次播放也有超时，失败时显示原因并释放采集资源。
- 若没有开始录音就准备失败，先确认关闭面板后 YouTube 本身能正常播放，再重新点击扩展图标。
- 已开始的采集失败时，可以点「停止生成」，或者在同一视频选择「重试本段」。若是广告中断，先恢复播放器并等广告结束。已确认的批次保留在本机，待确认的浏览器数据在明确释放前保留。
- 更新扩展后需要刷新视频页，以替换已注入的旧版面板脚本；不要在录音中途更新或刷新。

录制期间固定采集主播放器的视频元素；推荐视频预览、无关播放器的广告状态及可见面积变化不会作为切换视频的依据。
真正切换视频、移除主视频元素、替换主播放器或在当前播放器插入广告时仍会中断。
中断提示区分这些原因，清单保存有限的状态观测，供本地排查。旧版中断任务没有记录的原因不能事后推断。

## A. 1–2 分钟快速验证

- [ ] 先选择视频中部的一段，而不总从 0:00 开始，以便验证选区和时间记录。
- [ ] 使用默认 5 秒上传间隔开始录制，确认视频从选定起点播放。
- [ ] 录制过程中接收批次数和已保存字节数持续增长；扩展仅在收到匹配的保存确认后释放对应批次。
- [ ] 到达终点后等待最后一批及全部确认，再显示采集完成。
- [ ] 后端清单为 `status: complete`，`received_batches == expected_batches`，序号从 0 连续，缺失列表为空。
- [ ] 用下方工具验证各批哈希、字节数及合并文件，并执行本地解码。
- [ ] 用扩展中的音频播放入口回放合并录音，检查首尾是否为选中素材、是否有声音、是否有明显丢失或拼接跳跃。
- [ ] 保存此次采集，后续 Google 模块直接读取本机产物；不再为了调试反复录制。

`status: complete` 表示存储与批次完整性检查成功；音频可解码、内容正确还需要单独验证和试听。

## B. 5–10 分钟调参素材

- [ ] 默认 5 秒间隔录制一段 5–10 分钟素材，重复快速验证中的完整性、解码和试听检查。
- [ ] 记录选取时长、目标上传间隔、实际批次数、总字节数、最后一批确认等待时间，以及是否出现待确认批次持续积压。
- [ ] 播放时抽听开头、中间、结尾；本地解码仍需覆盖整份音频。
- [ ] 只有出现具体问题时才调整上传间隔。例如请求过密时增大间隔，单批数据或待确认占用过大时减小间隔；记录调整前后现象。
- [ ] 保留这份中等长度素材作为下游主要测试输入。无需预先确定最终上传间隔，也无需手动切音频。

上传间隔与后续 Google 识别窗口、GPT 文本批次互不绑定。保存的是单个 MediaRecorder 会话产生的连续容器片段，**不能逐个批次当作独立音频解码**。

## 离线校验与重建

在 `app/backend` 目录下运行。`CAPTURE_ID` 替换成扩展显示的任务 ID：

```sh
CAPTURE_ID="00000000-0000-4000-8000-000000000001"
.venv/bin/python capture_replay.py "../data/captures/$CAPTURE_ID" --decode
```

默认只读：检查已确认完成的清单、所有批次及已有 `recording.webm`。`--decode` 额外使用 `imageio-ffmpeg` 提供的本地 FFmpeg，把全部音频解码到空输出，并报告实际解码时长。也可显式指定本机二进制：

```sh
.venv/bin/python capture_replay.py "../data/captures/$CAPTURE_ID" --decode --ffmpeg /path/to/ffmpeg
```

如果希望从批次单独重建，可显式提供输出路径。只有批次和清单全部验证通过后才原子替换输出；不会修改清单或原始时间记录：

```sh
.venv/bin/python capture_replay.py "../data/captures/$CAPTURE_ID" \
  --output "../data/captures/$CAPTURE_ID/rebuilt.webm" --decode
```

输出为 JSON，包含任务 ID、批次数、总字节数、合并 SHA-256、原始时间观测；解码时另有 `decode_duration_sec`。默认不输出素材 URL、音频内容或本机绝对路径。校验失败返回非零退出码，不宣称采集完整。

工具不导入 Google/OpenAI 模块，不读取 `.env.local` 或 ADC，不发起云端请求。默认验证和解码均不产生云端费用。

## 时间记录的边界

清单保留录音启动、首次实际播放、停止时刻、播放器位置及可选的 `playing`/`waiting` 观测。批次还保存实际发出时的单调时间和可选 Blob timecode。

这些数据用于后续建立音频与视频时间映射。第一阶段不将「序号 × 上传间隔」当成时间轴，也不把短暂缓冲修正或精确音频 PTS 映射视为已经完成。实际解码时长与选区时长存在差异时，结合启动偏移和缓冲记录检查原因；后续接入转写时再校验句子到原视频的映射。

## 接口与保存产物

| 接口 | 用途 |
|---|---|
| `POST /captures` | 创建任务或重试相同元数据 |
| `POST /captures/{id}/timing` | 保存开始录音与实际播放的观测 |
| `PUT /captures/{id}/batches/{sequence}` | 保存批次，返回哈希和字节数确认 |
| `POST /captures/{id}/complete` | 声明批次数，验证并结束采集 |
| `GET /captures/{id}` | 查看状态、批次和缺失序号 |
| `GET /captures/{id}/audio` | 回放已完成的合并录音 |
| `POST /captures/{id}/abort` | 记录中断，保留已确认批次 |

本机产物位于 `app/data/captures/{id}/`：

- `manifest.json`：任务、选区、接收记录、原始时间观测、完整性状态。
- `batches/000000.webm` 等：原始上传批次。
- `recording.webm`：完成时按序合并的录音。
- 显式重建时产生的 `rebuilt.webm` 等文件。

`data/` 全部排除在 Git 之外。音频、素材 URL、浏览记录、清单和后续转写结果都可能含个人信息，不复制进测试源码、README、提交信息或 issue。测试代码使用临时目录和合成数据；密钥与项目配置继续只保存在被忽略的本机配置中。

## 自动测试与后续范围

离线自动测试覆盖重复上传、冲突、缺失批次、结束校验，以及回放工具的损坏数据处理与原子重建。它们用于确认基本数据契约，不能代替真实浏览器采集验收。

本阶段通过后，分别用保存的数据接入 Google 识别窗口和 GPT 文本批次。浏览器或后端重启恢复、长时间积压、30–40 分钟全链路压力及更完善的失败恢复留在后续阶段；基本确认、去重和完整性检查属于当前最小闭环。
